# TRPG学級会 — 設計方針書

TRPGドメインに特化した Polis 型の合意形成プラットフォーム。
本書は確定した方針の記録(初版 2026-08、最終更新 2026-09-01)。
2026-08-28 に公開、直後にSNSで拡散され初日10万PV超を記録。公開後の運用で
確定した方針は日付付きで追記している。

## 1. プロジェクトの目的

TRPG界隈ではSNS上の対立・論争が絶えない。賛成/反対/パスの投票と意見マップ
(Polis型)によって、レスバトルではなく「意見の地形図と合意点の発見」という形で
議論できる場を作る。参考: 日本版Polis (pol-is.jp)。

## 2. アーキテクチャ決定

**採用: 完全独自実装(Next.js + Vercel + red-dwarf)**

### 検討した選択肢と結論

| 案 | 内容 | 結論 |
| --- | --- | --- |
| A. 本家Polisをフォークしてセルフホスト | Clojure+Node+Python一式をVPS運用 | ✕ 一人運用には過大。セットアップ難・固定費・polyglot保守 |
| A'. 無改造の本家エンジンをセルフホスト+自前ポータル | エンジンだけ本家、UIは自前 | ✕ Bに対する固有の利点が薄い(正統性はred-dwarfで代替可) |
| C. ホスト版pol.is埋め込み+自前ポータル | pol-is.jp(PolisJAPAN)と同じ構造 | ✕ テーマ作成の自動化が非公式API依存になり、中核機能を外部の意向に握られる |
| **B. 完全独自実装** | エンジン込みで自前。クラスタリングはred-dwarf | **◎ 採用** |

### 決め手となった要件

1. **ユーザーによるテーマ投稿が機能要件** — C案では生命線が非公式APIになる
2. **完全アカウントレス設計** — 認証基盤が不要になりB案の開発量が縮む
3. **一覧の載せ方・ソート設計が中核的な差別化** — 体験全体を制御できる必要がある

### 経緯メモ

- pol-is.jp (PolisJAPAN) は本家のフォークではなく、ホスト版 pol.is の埋め込みラッパー
  (静的サイト+FastAPI Lambda)。テーマ作成は Selenium による画面自動操作で実現しており、
  この脆さが C 案を退けた主因
- チーム体制の PolisJAPAN でさえ本家エンジンのセルフホストを選ばなかった事実も A/A' 却下の根拠

## 3. プロダクト設計方針

### 参加モデル: 完全アカウントレス

- 投票・意見投稿・テーマ提案のすべてにアカウント不要
- 参加者は匿名cookieで識別(本家Polisと同じ方式)。参加済みかどうかの目印cookie
  (`gk_p`、値に意味なし)を併用し、未参加の閲覧者が個人化APIを呼ばずに済むようにする
  (2026-09-01、コスト対策)
- 保持する個人情報は悪用対策のIPハッシュのみ。**日替わりソルト**でハッシュ化するため
  日をまたぐと同一IPでも別の値になり、長期的な追跡・突き合わせが構造的にできない。
  記録自体も48時間で削除(実装は当初案の30日より強化)
- 多重投票は構造的に旨味が薄い(マップは多数決ではない)ことを透明性ページで説明する
- グループの「人数比」を主役にしないUIにして、水増しの動機をさらに削ぐ
- **投票の水増し対策**(2026-08-30): IP×テーマ単位のレート制限を導入。上限は
  「意見数×30(下限100)」で、同一IP(CGNAT等)に30人いてもフル参加できる水準に
  設定し、人間には実質届かず機械的な水増しだけが頭打ちになる。cookie側の枠は
  リセットで無意味化する(別参加者になれる)ため意図的に設けない。
  発動はログに記録し、誤検知(正規ユーザーの巻き添え)を監視できるようにする

### テーマ(議題)

- 匿名で提案可能。**事前審査なし・即時公開**(検閲をしない方針)
- スパム対策は内容ではなく流量で制御: Cloudflare Turnstile + レート制限
  (同一cookie・同一IPとも1日3件で運用)
- **構造的沈降**: 公開直後は「新着」タブのみ。10人が投票したテーマだけ
  人気タブに昇格する(閾値10人で確定)。人間のゲートは置かない
- ソートはHacker News方式の時間減衰ランキング(参加者数÷経過日数^減衰係数)。
  新しいテーマほど有利になり、古いテーマは参加者が多くても自然に沈む
- **類似テーマ検出と投票ゲート**(2026-08-31): 公開後にバズで同種テーマが乱立し、
  投票・意見が分散する問題が発生。提案時に既存の類似テーマを提示して合流を促す。
  検索も部分一致+埋め込みの意味検索ハイブリッドに拡張(表記が違っても内容が近い
  テーマを拾う)。埋め込みは自前ホストの小型モデル(ruri-v3-30m, ONNX)で計算し、
  外部AI APIへの送信はしない(下記のLLM不採用方針と整合)
- サーバーサイドLLMは載せない(コスト・悪用面から不採用)。ただし**ブラウザ内蔵AI
  (Chrome Prompt API / Gemini Nano)によるシード意見の下書き支援は例外採用**(2026-08-27)。
  端末内で動作するためコストゼロ・入力の外部送信なしで、当初の却下理由が該当しないため。
  対応環境でのみボタンが出るプログレッシブ・エンハンスメント

### 意見(ステートメント)

- 匿名で投稿可能。賛成/反対/パスの投票対象になる
- 公開方式は**即時公開のみで運用**(承認後公開は実装せず。テーマと同じく
  流量制御+事後モデレーションで支える。2026-08末の運用実績で問題なしと判断)

### モデレーション(削除)

- **事後対応のみ**(notice & takedown)。事前審査はしない
- 削除基準を狭く定義して公開する:
  実名個人への攻撃 / 個人情報の暴露 / 法令違反 / 機械的スパム — **のみ**
- 「不快である・論争的である」は削除理由にならないことを明記
- テーマ・意見に通報ボタンを設置。対応履歴はchangelogとして公開

## 4. 透明性の担保

「本家だから正しい」(C案)の代わりに「誰でも検証できるから正しい」を担保にする。

- クラスタリングは **red-dwarf** (Polis準拠の再実装、polis-community発、MPL 2.0)を
  デフォルトパラメータのまま使用。7票ルール(min_user_vote_threshold=7)、
  最大5グループ(max_group_count=5)、モデレーション適用ロジック等は本家Polis標準
- **「仕組み」ページ**を設置: 手法の日本語解説 + Polis論文(Small et al. 2021)・
  red-dwarfドキュメントへのリンク + 使用バージョンとパラメータの明記
- ~~匿名投票データのエクスポート~~ → **見送り方向で再検討(2026-08-27)**。
  検証可能性の担保として不完全(デプロイコードとの一致もデータの真正性も証明できない)な上、
  投票ベクトル全公開は匿名参加者の再識別リスクになるため
- モデレーション基準・運用パラメータの変更はルールページの記載を更新
- **コードのOSS公開を決定**(2026-09-01、MIT)。集計・クラスタリング・レート制限の
  実装を誰でも検証できることが「運営が数字を操作していない」ことの担保として機能する。
  荒らし対策の閾値も公開されるが、対策の強度は秘密性に依存しない設計
  (本当の秘密は環境変数のみ)なので問題にならない

## 5. 技術スタック

| レイヤ | 選定 |
| --- | --- |
| フレームワーク | Next.js (App Router) |
| ホスティング | Vercel (Fluid Compute) |
| DB | Neon Postgres (Vercel Marketplace) |
| クラスタリング | red-dwarf (Python, バージョン固定) を Vercel Python Function で実行 |
| 埋め込み(意味検索) | ruri-v3-30m (ONNX int8, Apache-2.0派生物) を Vercel Python Function で実行 |
| 再計算 | 投票トリガ(最短30分間隔)+日次Cronバックストップ |
| bot対策 | Cloudflare Turnstile |

- red-dwarf は「投票行列を渡すと座標とクラスタを返す」内部APIの裏に隔離し、
  将来差し替え可能なモジュールとして扱う(pre-1.0のためAPI変動リスクあり)

### 鮮度とコストの設計(2026-08-31〜09-01、バズ後のコスト最適化で確定)

初日10万PV超のバズで無料枠を大幅に超過したため、「全体は遅くてよい、個人は速く」
という原則でキャッシュ構成を確定した:

- **全体マップの再計算は30分間隔**。代わりに「自分の点」はクライアント側で
  ライブ投影し(公開されているPCA軸に自分の投票を掛けるだけ)、暫定グループも
  最近傍重心で即時判定する(本計算のk-meansと同じ割り当て規則の再現)。
  7票の参加基準に達するまではグレー表示、本計算が来たら公式の結果で上書き
- **テーマページはISR 30分キャッシュ**+内容が変わるイベント(意見投稿・削除対応・
  再計算完了)での即時無効化。参加人数などの数字だけCDN 60秒キャッシュの
  軽量APIから取得して鮮度を補う
- 個人化(自分の投票状態)はcookie依存のためページから分離し、クライアントから
  取得(ページ本体をCDNで共有可能に保つ)
- テーマ一覧の共有クエリはRuntime Cacheで60秒共有。一覧のリンク先読み(prefetch)は
  読まれない先読みがリクエストの過半を占めたため無効化
- 実績ランニングコスト: 最適化後はPro基本料$20+従量$10前後/月。定常トラフィックが
  十分下がればHobby+Neon Freeで月$0が成立する試算(観察中)

## 7. ライセンス・権利

- 自コードのライセンス: **MITで確定**(2026-09-01)。第三者著作物はMITの対象外として
  THIRD_PARTY_NOTICES.md で切り分ける(埋め込みモデル=Apache-2.0派生物、
  イラスト=Loose Drawing規約)
- **イラスト素材はリポジトリに同梱しない**(2026-09-01): Loose Drawingの規約は
  素材そのものの再配布を禁じており、公開リポジトリへの同梱はグレーになるため、
  セットアップ/ビルド時に公式サイトから取得するスクリプト方式を採用。
  git履歴からも素材ファイルを除去済み(公開時に全履歴が公開されるため)
- red-dwarf は MPL 2.0。ライブラリとして利用する限り自コードに伝播しない
  (red-dwarf自体のファイルを改変した場合のみ、その部分に公開義務)
- 権利リスクの整理(検討済み):
  - 著作権: 仕組み・アルゴリズムは保護対象外。本家コードのコピペをしなければ問題なし
  - 特許: 手法は論文・ドキュメントで全面公開されており、特許リスクは実質なし
  - 商標: 「Polis」の名称のみが実在するリスク → サービス名に使わないことで回避
  - 本家PolisのAGPL-3.0(ネットワーク経由のサービス提供でのソース公開義務)は、
    本家のコードを一切使っていないため**適用されない**(2026-09-01再確認)。
    広告等の収益化もライセンス面の障害はないことを確認済み(導入するかは別判断)

## 8. MVPスコープ(2026-08-28公開で完了)

1. テーマ提案・一覧・検索(新着タブ+昇格ロジック)
2. 意見投稿
3. 賛成/反対/パス投票
4. 2D意見マップ(red-dwarfによるクラスタリング表示)
5. 通報・削除フロー(狭い基準の公開込み)
6. 「仕組み」ページ(データエクスポートは §4 の通り見送り)

認証機能なし。LLM機能なし(ブラウザ内蔵AIの下書き支援のみ例外)。
